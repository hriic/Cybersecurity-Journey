# HTTP and Web Enumeration

HTTP is the language connecting browsers, APIs, proxies, web servers, and application frameworks. Strong web testing starts with understanding the request/response exchange before using vulnerability-specific tools.

## Request anatomy

An HTTP request contains a method, path, headers, and sometimes a body. Important headers can carry host information, authentication, cookies, content type, origin/referrer context, caching behavior, and client metadata.

## Response anatomy

A response contains a status code, headers, and usually a body. I compare all three because two requests can return the same status code while exposing very different behavior.

## Methods

- GET retrieves a resource.
- POST commonly submits data or triggers application logic.
- HEAD requests headers without the normal response body.
- OPTIONS can advertise supported methods/capabilities.
- PUT can create or replace a resource when supported.
- DELETE requests resource deletion.
- PROPFIND and MKCOL are associated with WebDAV.

A method being supported is not automatically a vulnerability.

## Status codes as evidence

- 2xx: successful handling.
- 3xx: redirection.
- 400: malformed/bad request.
- 401: authentication required.
- 403: understood but forbidden.
- 404: resource not found or intentionally hidden.
- 405: method not allowed.
- 500-series: server-side failure.

I treat status codes as clues and compare bodies, headers, redirects, and authentication challenges before drawing conclusions.

## Enumeration questions

For an authorized target I investigate:

- What web server or reverse proxy is visible?
- Which framework/application clues exist?
- What paths, files, APIs, and virtual hosts exist?
- What does robots.txt reveal?
- Are directory indexes enabled?
- Are backups or old files exposed?
- Which HTTP methods are supported?
- What authentication scheme is used?
- Which cookies maintain session state?
- Are errors verbose?
- Are security-sensitive headers missing?
- Is a response generated by the front web server or an upstream application?

## Content discovery

Content discovery is not just “find hidden directories.” I classify results:

- application routes;
- API endpoints;
- static assets;
- upload directories;
- backups;
- configuration artifacts;
- administrative/diagnostic pages;
- logs;
- debug functionality.

Then I manually verify interesting results to avoid wildcard/redirect false positives.

## Fingerprinting

Useful clues include server headers, cookies, error-page style, HTML/source, JavaScript bundles, framework artifacts, response timing, and route behavior.

Technology identification narrows research. Version strings and banners alone do not prove exploitability.

## Authentication and sessions

I separate:

authentication → who are you?

authorization → are you allowed to perform this action?

session management → how does the application remember authenticated state?

A valid session should never replace server-side authorization checks.

## Enumeration methodology

Baseline → fingerprint → discover content → inspect authentication/session behavior → map inputs → compare response differences → form a specific hypothesis → validate within scope → document evidence.

The key lesson is that enumeration is a reasoning process, not a command checklist.
